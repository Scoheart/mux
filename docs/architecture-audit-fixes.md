# 架构审计修复记录

对应 `analysis/10-architecture-bug-audit-2026-09-06.md` 的 v1.8.172 基线审计。

## 行为变化

| 审计项 | 修复 |
|---|---|
| B1 Qoder 私密恢复 | 恢复准入覆盖 Qoder CLI/Desktop；继续校验 reviewed paths、私密 ledger 和回滚 manifest，已提交操作可以完成清理。 |
| B2 当前模型被改变 | 凭据策略通过消费计划提交，保留 enabled/active。仅投递策略改变的已启用模型重新写入，停用模型不被启用。 |
| B3 策略失败部分残留 | 同一个 Agent 的凭据策略操作使用完整写入集合的原有持久化事务；任一模型失败会执行 CAS 回滚，不能只撤中央记录。无法安全恢复时保留恢复证据。 |
| B4 Qoder 共享 MCP | 计划发现相同路径与字段的其他消费者；会破坏另一消费者的单独移除、停用或清空被阻止。共同消费可以从中央消费者选择器在同一计划解除。共享消费者配置与状态进入前置条件。 |
| B5 模型发现凭据来源 | 目录发现按 Provider 的 Env/File/Helper/MuxStore 来源解析，遵守 Required/Optional/None；None 不发送凭据，兼容旧 Keychain 来源。 |
| B6 刷新遗漏 | 监听三个中央 catalog、MCP source 和新 Skills 内容目录；模型事件与全局重扫失效模型读缓存，已打开页面按 revision 重查，过期响应不会覆盖新数据。 |
| B7 网络持锁 | 短读锁中复制 Provider 与本地凭据快照，外部来源解析和 HTTP 在锁外执行；分页总网络预算 30 秒，单页最多 15 秒。 |
| B8 watcher 饥饿 | 提前过滤读取事件，256 项有界队列、按领域合并、最长 1 秒聚合窗口；溢出触发全域刷新。 |

共享 MCP 不具备物理上独立的开关：同一个 `mcpServers` 条目被多个产品读取时，MUX 会明确阻止冲突操作，而不会悄悄破坏另一产品。路径自定义必须同时得到 Agent 本身支持，单改 MUX 路径不能改变 Agent 的读取位置。

## 中央提交与目标恢复

模型 Profile/Provider 更新现在先保存中央数据与凭据，再按 Agent 将该 Provider 的所有受影响模型一起投递。每个 Agent 的完整文件集合用一个持久化完成记录标记，并绑定全部文件最终写入状态。同一文件后来又被部分改写时，旧完成记录不能用来跳过恢复。

普通 MCP/Model 消费变更、非重命名 MCP 更新和 Model Profile/Provider 更新采用中央提交检查点：中央已提交后，只恢复未完成的目标并记录对应 incident，保留中央数据、凭据与完成目标。失败目标通过后续显式重新应用收敛；不在启动时未经新的状态审阅重放旧内存草稿。

这是对报告中模型更新崩溃场景的修复，**不是整个事务系统已完成重构**：Skills 生命周期、Agent 路径迁移、中央删除等旧流程仍保留原恢复协议；凭据策略变更有意保留单目标整体回滚。旧版本没有中央检查点的 journal 继续按旧协议恢复，避免误把未完整保存的旧操作当作中央已提交。

## 验证边界

新增源码用例覆盖 Qoder 私密恢复的提交前/后窗口、凭据策略中第二个来源失效后的整体回退与当前模型保持、共享 MCP 的单独/共同解除、指定 File 来源与无认证请求、中央及成功目标的检查点保留。前端路由用例同步加入 models 失效任务。

本任务按仓库极速模式不执行测试套件、fmt、clippy、图标检查或 preflight。生产构建与正式发行包复验分别记录在交付结果中；新增测试源码不等于这些故障场景已经在运行时验证。没有以真实用户配置或 Keychain 执行故障注入。
